## 0. 三条前提（很重要）

1. 问题发生在**别人的电脑**上，我们没有那台机器的访问权限。任何结论都必须换算成「对方自己能执行的检查与修复」，命令要能直接复制粘贴。
2. 结论必须有依据：去仓库里找到对应代码 / 管道 / 已确诊案例；能在开发机用最小实验验证的就验证，验证不了就**明说「这是待确认的假设」**并给出确认方法。
3. **默认只读**：不要改仓库文件、不要在开发机上「顺手修掉」。排查结论交给作者，由作者决定是否改代码。

## 4. 交付格式（给 QQ 用户）

QQ 会吃掉换行，多行脚本经常「什么都没发生」。硬性要求：

- **单行、无注释、尽量 ASCII**；`#` 后面的内容会被吞掉并导致整段失效。
- 先判断再动作，输出人话结论（例如「★ 程序装在盘符根目录」）。
- 涉及删除 / 移动的命令必须有前置检查，别让用户误伤别的文件。
- **一次只给一步**，等他回报结果再给下一步。
- 优先给「看一眼就知道」的检查（资源管理器地址栏、界面版本号），命令是备选。

## 5. 已确诊案例库

> 格式：症状 / 原因 / 怎么让对方确认 / 怎么修 / 证据 / 关联提交。
> **只写实际确诊过的**；推测中的放 §6。

### 5.1 `Agent './python/python.exe' failed to start: Basepath argument is not fully qualified. (Parameter 'basePath')`

- **症状**：界面能正常打开、能进设置，但一启动任务就报这句，任务完全跑不起来。
- **原因**：程序被装在**盘符根目录**（例如 `E:\MFAAvalonia.exe`，安装目录就是 `E:\`）。
  UI 仓 `MFAAvalonia/Helper/AppPaths.cs`：
  `InstallRoot => AppContext.BaseDirectory.TrimEnd(Path.DirectorySeparatorChar, Path.AltDirectorySeparatorChar)`，
  它把 `"E:\"` 削成了 `"E:"`；而 `"E:"` 是「驱动器相对路径」，不是完全限定路径，
  于是 `AgentHelper.cs` 启动 Agent 的 `Path.GetFullPath("./python/python.exe", AppPaths.DataRoot)` 抛
  `ArgumentException: Basepath argument is not fully qualified. (Parameter 'basePath')`，被包装成用户看到的那句。
- **为什么界面一切正常**：`"E:" + "resource"` 这类拼接会碰巧解析到 `E:\resource`，所以界面、资源加载都没事，只有「要求完全限定基准路径」的 API 会炸。
- **让对方确认**：
  1. 看 `MFAAvalonia.exe` 所在目录——资源管理器地址栏若是 `E:\`（盘符后没有文件夹名）即确认；
  2. 或跑：`Get-PSDrive -PSProvider FileSystem | ForEach-Object { $r=$_.Root; if(Test-Path "$r\MFAAvalonia.exe"){ "★ 程序装在盘符根目录：$r  ← 就是它" } }`
- **怎么修**：关程序 → 在该盘新建文件夹（如 `E:\MFA`）→ 把根目录下那一整套程序文件**整体剪切**进去 → 从 `E:\MFA\MFAAvalonia.exe` 启动。
  一键版（单行，先关程序，`$d` 改成程序所在盘符）：
  ```
  $d='E:'; $dst="$d\MFA"; $sys=@('$RECYCLE.BIN','System Volume Information','pagefile.sys','swapfile.sys','hiberfil.sys','DumpStack.log','DumpStack.log.tmp','desktop.ini','bootmgr','Recovery','MSOCache'); if(-not (Test-Path "$d\MFAAvalonia.exe")){"在 $d\ 根目录没找到 MFAAvalonia.exe，请把开头的 `$d='E:' 改成程序所在盘符再跑"}elseif(Test-Path $dst){"目标 $dst 已存在，请先改名或删掉"}else{New-Item -ItemType Directory -Path $dst | Out-Null; Get-ChildItem "$d\" -Force | Where-Object { $sys -notcontains $_.Name } | Move-Item -Destination $dst -Force; "完成：已移动 " + (Get-ChildItem $dst -Force).Count + " 项到 $dst，请双击运行 $dst\MFAAvalonia.exe"}
  ```
- **注意**：加环境变量、改工作目录、管理员运行、换快捷方式**都没用**——路径取自 exe 位置，只能挪。
- **规则**：`MFAAvalonia.exe` 的所在目录不能是 `X:\`，必须是 `X:\某文件夹\`。
- **证据**：开发机 .NET 10 探针实测（`"E:\"` → 正常；`"E:"` → 抛的正是这条消息），探针在 `C:\Users\Aurora\Documents\ChatGPT\洛AA\pathprobe\`。
- **永久修复（待办，未提交）**：`AppPaths.InstallRoot` 加归一化——盘符根要保留分隔符：
  `trimmed.Length == 2 && trimmed[1] == ':' ? baseDirectory : trimmed`。已验证对普通路径行为不变、能编译通过。

### 5.2 启动崩溃：`The version of the native libSkiaSharp library (88.1) is incompatible ... [119.0, 120.0)`

- **症状**：程序一启动就崩，报 native `libSkiaSharp` 版本不兼容。
- **原因**：机器 `PATH` 上有**别的软件**带的 `libSkiaSharp.dll`，程序目录里自己的那份 native 缺失时，解析会回落到 `PATH`。
  实测踩到的是 `C:\Espressif\tools\git\mingw64\bin\libSkiaSharp.dll`（ESP-IDF 自带的 Git）。
- **让对方确认**：`where.exe libSkiaSharp.dll`（看有没有出现在别的软件目录）；同时看 `MFAAvalonia.exe` 同级有没有 `libSkiaSharp.dll`。
- **怎么修**：把程序自带的 `libSkiaSharp.dll`（及同批 native）放回 exe 同级；或先把 Espressif / 其它 Git 的 `bin` 从 PATH 里去掉再启动。
- **关联提交**：UI 仓 `16de115 fix: load bundled Skia native library before startup checks`（改 `MFAAvalonia/PrivatePathHelper.cs`、`MFAAvalonia.Desktop/Program.cs`）。
  新版应已免疫 → 用户还遇到就说明**版本旧**，先让他升级。

### 5.3 模拟器连不上：adb 拒绝连接（`10061 目标计算机积极拒绝`）

- **症状**：连不上 MuMu；`adb devices` 里出现的还是**别的设备**；手动 `adb connect <ip>:16384` 被拒。
- **原因**：MuMu 网络模式被设成**桥接**，实例想占用的 IP 已被局域网里别的设备占用
  （实测：MuMu 报 `adb_host_ip=192.168.1.6`，而那 IP 上是用户的华为手机 `LGE-AN10`）→ IP 冲突 → adb 端口根本没监听。
- **让对方确认**：
  1. `MuMuManager.exe info --vmindex 0` 看 `adb_host_ip`——正常应为 `127.0.0.1`；
  2. `Test-NetConnection <那个ip> -Port 16384` 返回 `False` 即端口没开。
- **怎么修**：MuMu 设置里把网络模式从「桥接」改回 **NAT / 默认**，重启实例；再确认 `adb connect 127.0.0.1:16384`。
- **背景知识**：MuMu 的 adb 端口约定从 16384 起、每实例 +32（instance0=16384、instance1=16416…），正常走回环。

### 5.4 主线刷取：扫荡结算页弹出「芯片仓库已达上限」后卡死、整个任务中断

- **症状**：一波刷完进入「扫荡成功」结算页时出现提示
  「芯片仓库已达上限，超过容量的芯片将通过邮件发送到邮箱中，请总队长注意查收。」；
  程序点了确定之后仍在结算页反复点却毫无反应，约 20 秒后任务中断（连带后面的任务也不跑了）。
- **原因**：那是**模态弹窗**——弹窗在的时候，点结算页的「扫荡成功」横幅是空点。
  而 `主线刷取_扫荡结算检查` 的 `next` 把弹窗处理排在点横幅之后，MaaFramework 的 `next`
  语义是「按顺序识别 next 中的每个节点，只执行第一个识别到的」（见 `deps/tools/pipeline.schema.json`）
  → 弹窗还在时一直先点横幅，把 `max_hit`（当时 =3）提前耗光；等弹窗终于被点掉，
  结算节点已经用完次数、再没有节点能点横幅，画面静止到 20 秒识别超时
  → `Node.NextList.Failed` → 任务队列中断。
- **让对方确认**：在 `debug\maafw.log` 里搜 `主线刷取_扫荡结算检查`。若看到连续几条点位不同
  （如 `pt=269,39` / `pt=221,83` / `pt=183,90`），随后一条 `主线刷取_意外_芯片仓满 pt=639,448`，
  紧接着约 20 秒无新动作 → 即本案例。
- **怎么修**：升级到 2026-09-22 之后、含 `tools/test_mainstory_settlement.py` 的版本。
  该弹窗按**偶发容错**处理，不进入正式流程：
  1. `[JumpBack]主线刷取_意外_芯片仓满` 前置到 `扫荡中` / `扫荡结算检查` 两条 next 的首位；
  2. `主线刷取_扫荡结算检查.max_hit` 3 → 10（留出被弹窗空点的余量）；
  3. 补有界出口：`on_error → 主线刷取_结算收尾_兜底`（DirectHit 中继）`→ 主线刷取_刷取完成`，
     再也不会以 `NextList.Failed` 收场。
  没有弹窗时正常路径一字未改（`扫荡中 点1次 → 结算检查 点1次 → 回到关卡详情`）。
- **判据 / 背景**：框架的 `interrupt` 字段自 **5.1 起废弃，官方推荐用 `[JumpBack]` 替代**；
  `[JumpBack]X` 只在 X **识别到时**才执行、执行完回到调用方的列表，所以它天然是容错而不是正式步骤。
  历史成功样本（09-17 11:48 / 12:50、09-18、09-19、09-20）都是「各点 1 次就回到关卡详情」，
  可用来判断正常水位；点位落在「扫荡成功」横幅框 `29,30,350,102` 内属正常。
- **证据**：2026-09-22 10:13 那次任务，`install/debug/maafw.log`：
  `10:14:18.938 扫荡中 pt=144,56` → `10:14:21/24/26 结算检查 pt=269,39 / 221,83 / 183,90` → 
  `10:14:28.205 意外_芯片仓满 pt=639,448`（弹窗消失）→ `10:14:29~10:14:48` 画面静止 19 秒 →
  `10:14:49 Node.NextList.Failed`；结算页残留 OCR：`592,310 扫荡次数`、`800,327 EXP`、`848,357 180`。

## 6. 常见方向（**未确诊**，先往这看，别当结论念给用户）

- **Agent 起不来但没有 `basePath` 字样** → 看 `logs\log-YYYYMMDD.log` 有没有 Python traceback；`python\` 目录是否被杀软隔离或误删；`Install-Agent-Deps.bat` 是否跑过。
- **认不到图 / 点不准** → 先别怀疑代码：确认模拟器分辨率与 DPI（本项目 pipeline 以 **1280×720** 为基准坐标）、画质/特效是否遮挡 UI、是否换了机型或换了模拟器。
- **改了 `interface.json` / 选项不生效** → MFA 需要重启才会重读，用户侧让他重启程序。
- **连接模拟器卡 60 秒** → 见 `README-DS.md` §9（pretask 排查）。
- **更新失败 / 更新后打不开** → UI 仓 `VersionChecker`、`MFAUpdater`；先要 `backup\` 目录与更新日志。
