## 一、这件事要做什么

把**活动**（Activity）里那套「刷关票消耗方式」搬进**每日探索**，改名「体力消耗方式」，
替换掉原来的「是否手动选择次数(开启燃料使用)」，并**成为次数的生成位**。

沿用活动逻辑：**算**（识别当前体力 → 按关卡消耗算出次数），不再靠红/白来回试错。
- 「消耗完体力」：用掉用户选的体力药后，执行原有的消耗完所有体力流程
- 「指定次数」：算出所需体力，用体力药补差额；超过 10 次分批执行

**次数的唯一来源（用户确认的公式）**：

```
次数 = 当前体力 ÷ 单次消耗        当前体力 = 识别到的体力 + 用掉的体力药恢复量
```

本次已完成的就是这条公式的落地：扫荡弹窗里**不再有**红/白/增减试错循环。

**整条链（两种模式共用同一个入口）**：

```
每日探索_第几层
  → 每日探索_体力药准备(prepare)   读设置 → 读当前体力 → 算计划 → 认领本次药量
  → 分派（按 next 顺序逐个识别）：
        ├─ 每日探索_计划结束收尾   plan:finished  → finish 动作 → 出击任务列表（正常结束）
        ├─ 每日探索_待使用体力药   potion:pending → 打开体力药 → 药量页 → 确认 → 回关卡页
        └─ 扫荡                    （DirectHit 兜底）
  → 扫荡 → 扫荡次数选择
  → 每日探索_扫荡弹窗已打开         先确认弹窗在（OCR「现在」「扫荡后」）
        ├─ 消耗完体力 → 每日探索_按体力计算次数
        └─ 指定次数   → 每日探索_按次数扫荡
  → 开始战斗 → 开启加成（双倍确认，两模式都过）
```

- **`prepare` 的返回值**：正常一律 `True`（交给分派节点按识别决定下一步）；
  只有「读不到设置 / 读不到体力 / 一次要超过 50 瓶」才 `False`（真错误 → `on_error`）。
  「不需要补药」不再用 `False` 表达 —— 那会踩 `on_error: ["扫荡"]` 这条边，
  而 MaaFW 的 `on_error` 在 action 返回 False 时到底走不走，Python 层没有文档，不能赌。
- `final_stamina` 由 `plan_consume_all` 算出 = 起始体力 + 计划用掉的药量（`stamina_cost + stamina_left`），
  也就是「体力药用完之后、把计划里的扫荡都做完时」的体力；次数取它除以 `cost`。
- 次数上限 10 是游戏弹窗的限制（`BATCH_LIMIT`）；剩余体力要接着扫需要下一批（见第七节限制）。
- **失败即停**：算不出体力/消耗、体力不够一次、一次要超过 50 瓶、弹窗读数不可信 —— 一律报错退出，绝不盲点。

**⚠️「指定次数 + 不使用体力药」体力不够：正常结束，不是失败**

用户要求：自选次数做不到就**一次都别扫**（扫一半白花体力），日志提示
`当前自选次数X次，体力不足，未执行刷取操作`，而且**任务按正常结束**，不能算失败。

```
_build_plan: 指定次数 且 不使用体力药 且 summary.shortfall
   → log「当前自选次数X次，体力不足，未执行刷取操作（当前体力=…，单次消耗=…，最多只能扫N次）」
   → _SESSION["plan_finished"] = "insufficient_stamina"；batches=[]；返回 False
prepare:     见 plan_finished → 返回 True → 分派节点
plan:finished 命中 → finish 动作（什么都不点，只打日志）→ 出击任务列表 → 任务成功结束
```

- 双保险：`set_sweep_count_by_stamina` / `set_sweep_count` 开头都检查 `plan_aborted`，
  命中就 `return False`，保证「一下都不点」。
- ⚠️ 收尾由 `plan_finished` 驱动，**不是** `plan_aborted`：`_load_settings` 每次都
  `_SESSION.clear()`，所以标记必须在 `prepare` **开头**就判断，否则第二趟会被清掉。

**⚠️ 00:37 又判死一次：输入框读法错了，计划整个是空的**

症状：`准备 → 扫荡` 直接跳过去，没进体力药链，扫荡弹窗里次数也没配，
`每日探索_按次数扫荡` 的 `batch:pending` 反复不命中直到超时。

根因：**`_input_int` 读的是 `item["input"]` 数组，而 MFA 把值存在 `item["data"]` 里**：

```json
{ "name": "每日探索_体力药数量", "index": 0,
  "data": { "使用数量": "1", "体力药数量": "1" } }
```

于是 `custom_runs` 永远读成默认 **0**、`potion_count` 永远读成 1 →
`plan_actions(0, …)` 直接返回空计划（`batches=[]`、`potion_steps=[]`）→
两个识别都不命中 → 落到 `扫荡`，游戏用旧选择的次数显示 `-6`。

修法（照活动 `_input_int` 的形状）：
1. 先读 `item["data"]`；
2. **按接口 `option.<名>.inputs[].name` 声明的输入名精确取**
   （`data` 里可能有历史残留键，如 `{使用数量, 体力药数量}` 并存，取第一个会读到错的值）；
3. 再退回 `input` / `inputs` 数组，最后才用默认值。

实机配置（`install/config/instances/default.json`，`每日探索` 任务）实测读到：

```
关卡选择=荒墟拾遗（遗余之谱）  第几层=不选择-默认打最高  → cost=35
体力消耗方式=指定次数   体力药=使用(小药)   自定次数=2
→ 计划：体力 29 → 补 5 瓶小药（缺 41）→ 扫 2 次 ✅
```

**排查这类问题的手法**：agent 的 INFO 日志**不进 MFA 日志**（只有 WARNING/ERROR 会进
`install/logs/log-*.log`），所以「日志里什么错误都没有、但流程不对」时，
**直接读 `install/config/instances/default.json` 看真实选项值**，别去猜。

**核对六件事**（日志 + 弹窗截图）：
1. `每日探索体力设置` 里的「单次消耗」是否等于关卡表里该关该层的燃料；
2. `当前体力稳定读取=` 的读数是否等于游戏里真实体力；
3. `本次准备使用体力药 N 瓶` 与体力缺口是否吻合（缺口 ÷ 药量，向上取整）；
4. `按体力计算扫荡次数` / `扫荡次数复核成功：次数=N，现在=X，扫荡后=Y` 里的 Y 对不对；
5. **双倍确认弹窗照旧出现**（见下）：`开始战斗` 后应命中 `开启加成`（或 `每日探索_扫荡双倍`），
   按「每日探索掉落加成」的 Yes/No 点击对应按钮，别被新的次数节点挤掉；
6. 「指定次数 + 不使用体力药 + 体力不够」时，日志出现
   `当前自选次数X次，体力不足，未执行刷取操作`，**且任务显示成功而不是失败**。

**双倍确认链（本轮一行未动，已加测试护栏）**
- 开关：`interface.json` 的 `每日探索掉落加成`（label「是否使用双倍」，默认 Yes）覆盖 `开启加成` 的
  `roi` + `expected`（Yes 点「使用」，No 点「不使用」）。
- 两处确认位：`通用-扫荡.json` 的 `开启加成`（next 含 `每日探索_芯片仓库上限确认` / `扫荡成功`）、
  `每日探索.json` 的 `每日探索_扫荡双倍`（`每日探索_开始战斗` 的 `[JumpBack]` 首位，该节点当前 enabled=false，属既有状态）。
- 本轮只改了「次数从哪来」：两条入口 `每日探索_按体力计算次数`、`每日探索_按次数扫荡` 都落在 `开始战斗`，
  而 `开始战斗` 的 next 仍含 `开启加成`；`每日探索_已回到关卡页` 仍只接 `扫荡`。
- 护栏在 `tools/test_daily_stamina_dialog.py` 的
  `test_sweep_count_step_still_goes_through_double_reward` / `test_double_reward_option_still_wired`。
- **双倍只按单次消耗扣体力**（用户确认），所以 `次数 = 体力 ÷ 单次消耗` 不需要为双倍加系数。

**实机前先确认 UI 里有「体力消耗方式」下拉**（消耗完体力 / 指定次数）。
如果只有老的「是否手动选择次数」，说明 interface.json 又被回退了 —— 跑
`tools/test_daily_stamina_dialog.py::test_stamina_mode_option_is_reachable_in_the_ui` 能立刻发现。

**已知限制（本轮没动，遗留）**：
- 「消耗完体力」只扫**一批**（最多 10 次）。`扫荡结束` 的 `next` 在关卡选择里被重写成 `进入首页`，
  一批扫完任务就结束；体力 > 10×单次消耗时，剩下的体力要再跑一次任务才会被消耗。
  想一次扫干净需要把 `扫荡结束` 接回 `扫荡次数选择`（绕开体力药链，避免重复补药），改动面较大，未做。
- 「指定次数」模式的 `每日探索_按次数扫荡` / `每日探索_下一批` 走的是另一条链，本轮未改。
- 活动的 `>25` 快路径（先按最大键到 50 再减）**未在实机跑过**。
- `检查体力-白-放宽` 的阈值 205 **未实测**，且本流程已不再引用该节点。

## 八、踩过的坑（别重复）

1. **只改 `assets/` 不同步 `install/`** → UI 完全没变化。必须同步 + 重启 MFA。
2. **坐标不能猜**。`(300,430)` 猜错一次，卡了两轮。实机取色/OCR 定位后再写。
3. **自愈重试必须先等页面过渡**。点完就判 → 假失败 → 重试补刀 → 把页面点飞。
4. **不要自己发明返回逻辑**。用户原话：「直接按照活动现有的后续处理抄」。
5. 改 pipeline JSON 的脚本**务必先验证 JSON 合法再写盘**（本次写出过一个坏 JSON，靠事后 grep 修回）。
6. 用 `json.loads` + `json.dumps` 批量改 `interface.json` 会**把整个文件重排**（393 增 94 删的假 diff）。
   要改就得**字符串级精修**，改完 `git diff --stat` 确认只有目标几行。
7. `tasker.post_recognition` 直调 OCR 在本机返回空；**只有 Pipeline 节点路径能拿到文字**。
8. `tools/test_*.py` 里读 `_SESSION` 时**必须 `dict()` 拷贝**：测试的 `finally` 会 `clear()` 同一本字典，
   返回引用会让断言全部 KeyError。
9. 脚本改 JSON 时注意：新增节点**末尾要带逗号**，且每个节点必须有 `$__mpe_code.position`。
10. PowerShell 里跑 `.venv\Scripts\python.exe -c "…"` 传含引号的代码会被剥引号；
    写成临时 `.py` 文件再跑。
11. **文件会「变回去」**：同一份 `interface.json` 在不同时刻读到的内容不一致（选项定义丢失、
    文件 mtime 却早于本次开工）。动手改 interface/pipeline 前**先确认 MFA 已关闭**，
    改完立刻 `git diff --stat` + 跑测试核对，别相信上一轮记忆里的状态。
12. **别照抄交接文档里的 ROI 就去写代码**。`ROI_SWEEP_COUNT` 就是这么翻车的：文档写着「与
    `次数到10次` ROI 一致 ✅」，实机 OCR 直接读空。MFA 出错时会把现场图存到
    `install/debug/on_error/`，**先用 `tools/ocr_screenshot.py` 在那张图上验证 ROI**，再动代码。
13. **先看活动怎么做的**。用户原话：「根据现有活动流程类似复用就行了」。读次数这件事活动
    早就绕过去了（读「扫荡后」反推），自己另起一套必然踩坑。
14. **读选项看 `item["data"]`，不是 `item["input"]`**。这是 00:37 判死的直接原因：
    `custom_runs` / `potion_count` 全被读成默认值，计划变空。
    而且 `data` 里可能有历史残留键，要按接口 `inputs[].name` 精确取。
15. **agent 的 INFO 日志不进 MFA 日志**（只有 WARNING/ERROR 进
    `install/logs/log-*.log`）。「没有任何错误但流程不对」时，去读
    `install/config/instances/default.json` 看真实选项值。
