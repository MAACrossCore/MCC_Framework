# 活动任务维护说明

## 目标

“活动”任务使用固定底层流程，活动更新时优先只替换 Pipeline 中的页面特征和点击坐标。Agent 不负责页面跳转，只负责读取设置、记录执行状态、选择队伍、读取票数和校验扫荡次数。

## 当前流程

主界面 -> 活动首页 -> 任务奖励 -> 一键领取 -> 活动首页 -> 读取体力与刷关票并规划资源 -> 按模式使用体力药 -> 活动首页 -> 兑换站点 -> 认证权限卡 -> 选择实际可兑换数量 -> 购买并领取 -> 活动首页 -> 困难模式 -> 第一关 -> 扫荡弹窗 -> 切换队伍 -> 读取刷关票 -> 分批调整次数 -> 复核“扫荡后”票数 -> 第一次点击加速结算 -> 等待 -> 第二次点击退出 -> 确认战斗选择页 -> 返回主界面。

任务可以从活动首页、任务奖励页、困难模式页、困难关战斗选择页和扫荡弹窗接续。兑换站点与购买弹窗不作为初始化入口，避免缺少本轮状态时误记兑换完成。

## 文件职责

- `assets/resource/pipeline/base/活动.json`：当前活动的页面识别、点击坐标和完整流程。
- `assets/resource/pipeline/base/通用-队伍与扫荡.json`：队伍选择、票数读取、分批次数调整和掉落加成选择。
- `assets/resource/pipeline/base/通用-体力药.json`：库存读取、小药/大药选择、数量调整、结果领取、分批与关闭页面。
- `agent/activity_pipeline.py`：配置读取、资源规划、运行状态、体力药库存/数量 OCR、队伍编号点击、票数 OCR、批次计算和“扫荡后”数量复核。
- `assets/interface.json`：活动任务设置。

发布目录下的同名文件需要与上述源文件保持一致。MPE 元数据直接保存在三个 Pipeline JSON 的 `$__mpe_*` 字段中。

## 活动更新时通常要替换的节点

- `活动_主界面已到` 的活动入口点击坐标。
- `活动_活动页已到` 的页面文字特征。
- `活动_待领取每日票` 的“奖励内容”入口坐标。
- `活动_待兑换刷关票` 的兑换站入口坐标。
- `活动_选择认证权限卡` 的票商品特征和坐标。
- `活动_待规划资源` 的 `stamina_cost_per_ticket` 是单张票消耗体力，当前为 `15`；`ticket_cost_per_run` 是单次扫荡耗票，当前为 `2`。
- `活动_进入困难关`、`活动_点击困难模式线条` 的特征和坐标，以及
  `活动_困难第一关_研究所` 的 `expected` 与 `roi`。困难第一关定位采用
  “连续向右拖拽两次 -> OCR 第一关文字 -> 未命中则重复两次拖拽”的通用循环；
  OCR 命中后直接点击识别到的文字框，不使用固定关卡点击坐标。
- 活动票图标或数量位置改变时，调整 Agent 中 `ROI_TICKET_CURRENT` 和 `ROI_TICKET_AFTER`。

## 通常保持不变的逻辑

- “消耗完当前体力”先使用用户指定药量，再兑换当前体力允许的最大票数；只有该模式显示药量输入框。
- “自定次数”按目标扫荡次数自动计算所需票、应购票、所需体力和体力药数量；目标超过实际资源时按最大可执行量继续并记录日志。
- 体力药“不使用/使用”分支与类型设置；每批上限 50，数量页调整后必须 OCR 复核，超过 50 时循环分批。
- 体力药库存仅剩 1 个时，点击使用可能直接进入结果页而不显示数量页；该路径按本轮实际使用 1 个处理。
- 队伍 01 至 04 的通用选择逻辑。
- 单次扫荡上限、每关耗票量、奇数票舍弃 1 张的计算。
- 超过单批上限时分批扫荡。
- 每次调整后核对“扫荡后”数量，核对成功才开始战斗。
- “使用每日双倍掉落”勾选框和扫荡结算循环；勾选点击“使用”，未勾选点击“不使用”。
- 结算页固定在角色 ID 正上方的左侧空白区 `(300, 430)` 执行两次点击：第一次后等待 `1800ms`，第二次后等待 `1200ms`；识别到战斗选择页的“扫荡”按钮并稳定等待 `1500ms` 后，才允许扣减内存中的剩余次数。

## 坐标与分辨率

录制器保存的是模拟器原始截图坐标。当前 Pipeline 使用 `1280x720` 基准坐标；例如录制为 `1920x1080` 时，横纵坐标均除以 `1.5`。MaaFramework 会把基准坐标和 ROI 映射到实际控制分辨率，因此不要为每个分辨率复制一套节点。

## 修改检查清单

1. 用录制内容确认入口、页面特征、目标按钮和返回路径。
2. 只替换上述易变节点；除非玩法规则改变，不改 Agent 的批次算法。
3. 检查两个 JSON 均可解析，并检查 Agent 可编译。
4. 在 MFA 中用实际设置完整运行：兑换一次、选择指定队伍、调整扫荡次数、核对“扫荡后”、完成结算并返回主页。
5. 使用体力药时，额外核对数量 OCR、结果页、两层关闭和重新识别活动首页；不要用高级燃料重复测试仅 1 个库存的分支。
6. 查看日志中是否依次出现“自定数量复核成功”“体力兑换刷关票完成”“扫荡次数复核成功”“单轮扫荡结算完成”“活动任务完成”。
7. 实机流程确认后，再补充必要的等待、重试和分辨率验证。

## MPE 维护约定

- 每个实际节点都保留 `$__mpe_code.position`；外部通用节点在 `活动.json` 顶部使用 `$__mpe_external_*` 表示。
- 页面跳转和执行顺序只写在 Pipeline JSON；Agent 不复制流程图，也不决定跳到哪个页面。
- 新活动沿用现有节点职责，优先只改“活动更新时通常要替换的节点”所列识别内容和坐标。
- 不保留失效入口、猜测页面或不会在正常链路中执行的兜底分支。新增分支必须有录制依据，并能说明从哪个页面进入、以哪个页面结束。

## 当前边界

普通体力药已完成 `3` 瓶数量调整、OCR 复核、换票、扫荡、结算和返回主页的整链实机验证。高级燃料不再重复消耗验证。体力药库存少于计划值时，程序按实际库存使用，并在日志中记录计划值和实际值后继续执行。
